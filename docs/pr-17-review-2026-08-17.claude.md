# Код-ревью PR #17: chore(deploy): run unprivileged, keep secrets out of the config, support tls

Дата: 2026-08-17. Ветка `chore/deploy-hardening` → `feat/distributed-watch`, коммит `ef48efb`.

## Что делает PR

Четыре независимых изменения в одном коммите, 15 файлов, +419/-62:

1. **Непривилегированный запуск.** [`Dockerfile`](../deploy/Dockerfile#L28) заводит UID 10001 и переключается на него; [`deployment.yaml`](../deploy/k8s/deployment.yaml#L24) получает pod- и container-level `securityContext` (`runAsNonRoot`, `readOnlyRootFilesystem`, `drop: [ALL]`, `seccompProfile: RuntimeDefault`) и два `emptyDir` под `/data/results` и `/tmp`.
2. **Подстановка `${VAR}` из окружения** в [`internal/config/config.go`](../internal/config/config.go#L175). Чинит issue #5: `dbbridge-$(POD_NAME)` в ConfigMap оставался литералом, обе реплики рапортовали один instance ID. Тем же механизмом Redis-пароль, S3-ключи и адреса выносятся в [`secret.yaml`](../deploy/k8s/secret.yaml).
3. **TLS** для всех трёх листенеров через `server.tls.{cert_file,key_file}` в [`main.go`](../cmd/dbbridge/main.go#L236); h2c без сертификата теперь требует явного `allow_h2c`, иначе печатается предупреждение.
4. **Dev-стек:** Redis без публикации порта и с паролем, MinIO-бакет больше не анонимно-читаемый, `/metrics` переехал на admin-листенер (8181/8182), Prometheus скрейпит его.

## Итог

Направление правильное, и три из четырёх частей сделаны аккуратно: securityContext согласован с тем, что код реально пишет на диск, отчёт reload не тащит DSN, `authn` падает закрыто. Сборка, `go vet`, `gofmt` и тесты `./internal/config/...`, `./internal/transport/...` проходят чисто.

Но центральный механизм PR - подстановка `${VAR}` - реализован текстовой заменой в сыром YAML **до** парсинга. Это ломается на легальных значениях секретов: пароль с кавычкой или обратным слэшем валит старт с посторонней ошибкой, а пароль с завершающим переводом строки (типовой результат `kubectl create secret --from-file` и `echo | base64`) **молча** превращается в другую строку. Для PR, чья заявленная цель - «вынести секреты в окружение», это блокер: чинится небольшой правкой (подстановка по дереву `yaml.Node` вместо текста).

Второе, что стоит поправить до мерджа: эталонный k8s-деплой из коробки не стартует (два одинаковых плейсхолдера токенов), и ошибка не указывает на причину.

Находок: 1 блокер, 4 важных, 11 мелочей.

## Блокеры

### Подстановка `${VAR}` работает по тексту YAML и портит значения секретов

[`internal/config/config.go#L175`](../internal/config/config.go#L175), вызов в [`Reload`](../internal/config/config.go#L199).

`expandEnv` заменяет `${VAR}` в байтах файла, после чего результат идёт в `yaml.Unmarshal`. Значение переменной становится частью YAML-разметки, а не остаётся данными. Проверено запуском `NewManager` на конфиге `redis_password: "${ZZ_PWD}"`:

| Значение переменной | Что получается |
|---|---|
| `pa"ss` | старт падает: `failed to unmarshal yaml: yaml: line 1: did not find expected key` |
| `pa\ss` | старт падает: `yaml: line 4: found unknown escape character` |
| `secret\n` (перевод строки в конце) | **молча** становится `"secret "` - с пробелом на конце |
| `x"` + перевод строки + `instance2: injected` | пароль молча становится `x`, остальное разбирается как YAML |

Самый вероятный сценарий - третья строка. `kubectl create secret generic dbbridge-secrets --from-file=REDIS_PASSWORD=pw.txt` или `echo "$PW" \| base64` кладут в Secret значение с `\n` на конце. Вход: Redis-пароль `s3cret`; результат: приложение подключается с паролем `s3cret ` и получает `WRONGPASS`, а оператор ищет проблему в Redis, а не в конфиге. Для `S3_SECRET_ACCESS_KEY` - то же самое, но отказ проявится только на первой записи результата. Первые две строки таблицы менее опасны (падение громкое), но номер строки в сообщении не соответствует файлу и имя переменной не названо, так что диагностика тоже нетривиальна.

Четвёртая строка - YAML-инъекция из значения переменной. Источник данных - оператор, поэтому как атака это слабо, но как механизм тихого искажения конфига - тот же класс.

Исправление: раскрывать `${VAR}` не в тексте, а после парсинга - обойти дерево `yaml.Node` и подставлять только в скалярах (`node.Kind == yaml.ScalarNode`), затем `node.Decode(&cfg)`. Тогда значение никогда не интерпретируется как разметка, спецсимволы сохраняются буквально, и заодно снимается находка про комментарии (см. «Мелочи»). Как ориентир, в этом же репозитории секрет уже вводится правильно: `auth.tokens[].value_env` читается через `os.Getenv` в [`authn.New`](../internal/authn/authn.go#L90), минуя YAML.

## Важное

### Эталонный k8s-деплой не стартует с приложенным `secret.yaml`

[`deploy/k8s/secret.yaml#L15`](../deploy/k8s/secret.yaml#L15).

`DBBRIDGE_TOKEN_REPORTING` и `DBBRIDGE_TOKEN_ADMIN` заданы одинаковым плейсхолдером `change-me`. [`authn.New`](../internal/authn/authn.go#L99) отвергает совпадающие значения токенов, поэтому `make k8s-apply` (который применяет весь каталог, включая Secret) даёт CrashLoopBackOff с сообщением `Failed to initialize authentication: auth token 1 (orchestrator): duplicate value`. Проверено вызовом `authn.New` с двумя спеками и одинаковым значением в окружении.

Отказ по сути правильный - лучше не подняться, чем подняться с общеизвестным токеном, - но сообщение не указывает на `secret.yaml`, а README обещает рабочий `make k8s-apply`.

Исправление: переименовать в `deploy/k8s/secret.example.yaml`, чтобы `kubectl apply -f deploy/k8s/` его не подхватывал. Тогда под встанет в `CreateContainerConfigError` с текстом `secret "dbbridge-secrets" not found`, который прямо называет недостающий объект. README уже требует «replace every placeholder», достаточно поменять формулировку на «скопируйте example и заполните».

### Включение `server.tls` ломает probes и скрейп Prometheus в поставляемых манифестах

[`deployment.yaml#L69`](../deploy/k8s/deployment.yaml#L69) (probes), [`deployment.yaml#L20`](../deploy/k8s/deployment.yaml#L20) (аннотация), [`prometheus.yml#L8`](../deploy/prometheus.yml#L8).

TLS в [`main.go`](../cmd/dbbridge/main.go#L246) включается сразу для всех трёх листенеров, отдельного переключателя на listener нет. При этом в манифестах `livenessProbe`/`readinessProbe` заданы как `httpGet` без `scheme: HTTPS` (по умолчанию `HTTP`), аннотация `prometheus.io/scheme` отсутствует, тома для сертификата в поде нет, а README описывает `server.tls.cert_file / key_file` как обычную опцию конфига.

Вход: оператор дописывает `cert_file`/`key_file` в ConfigMap согласно README и раскатывает. Результат: kubelet шлёт открытый HTTP на TLS-порт, liveness-проба не проходит, под уходит в бесконечный рестарт; Prometheus теряет цель. При этом сам процесс работает, поэтому причина неочевидна.

Исправление: либо добавить в `deployment.yaml` закомментированный вариант с `scheme: HTTPS`, аннотацией `prometheus.io/scheme: "https"` и томом с TLS-секретом, либо явно написать в README, что в k8s TLS терминируется на ingress, а `server.tls` предназначен для деплоев без него.

### Сертификат читается один раз, ротация требует рестарта, и это нигде не сказано

[`main.go#L247`](../cmd/dbbridge/main.go#L247).

`srv.ListenAndServeTLS(cert, key)` читает пару при старте и держит её в памяти. Файлы больше не перечитываются: `tls := cfg.Server.TLS` - снимок конфига, а горячий reload по построению помечает секцию `server` как ignored ([`diff.go#L20`](../internal/config/diff.go#L20)) и листенеры не пересоздаёт.

Вход: cert-manager обновляет Secret с сертификатом за сутки до истечения. Результат: под продолжает отдавать старый сертификат до ближайшего рестарта; после истечения - полный отказ всех трёх листенеров, при том что `/v1/admin/reload` отвечает `success: true`.

Исправление: `&tls.Config{GetCertificate: ...}` с перечитыванием файла (кэш по mtime) - это десяток строк и снимает проблему полностью. Минимальный вариант - строка в `deploy/README.md` о том, что ротация сертификата требует рестарта пода.

### `trusted_proxy_count: 1` в ConfigMap при отсутствии L7-прокси в манифестах

[`configmap.yaml#L33`](../deploy/k8s/configmap.yaml#L33).

Значение 1 включает [`ClientIPFromXFFTrustedProxies(1)`](../internal/transport/rest/server.go#L111), то есть крайняя правая запись `X-Forwarded-For` считается адресом клиента. В `deploy/k8s/` есть только ClusterIP-Service - L4-балансировка, которая заголовок не добавляет и не переписывает. Ingress-манифеста в комплекте нет.

Вход: `curl -H 'X-Forwarded-For: 10.0.0.1' http://<pod-ip>:8080/v1/queries`. Результат: в логах и во всём, что опирается на адрес клиента, окажется подставленное значение. Само по себе на этом коммите это только логи, но следующий PR в стеке добавляет rate limit на вызывающего, и там подделываемый ключ уже означает обход лимита ротацией заголовка.

Исправление: оставить `trusted_proxy_count: 0` и в комментарии написать «поставьте 1, когда перед сервисом появится ingress, который добавляет X-Forwarded-For».

## Мелочи и предложения

- **`${VAR}` в комментарии конфига тоже раскрывается.** [`config.go#L177`](../internal/config/config.go#L177) идёт по всему файлу, включая комментарии. Проверено: конфиг со строкой `# example: redis_password: "${SOME_UNSET_VAR}"` не грузится - `unset environment variables referenced by the config: SOME_UNSET_VAR`. Неприятно ровно потому, что README учит писать `${VAR}`, и естественное желание - показать пример в комментарии. Постпарсинговая подстановка (см. блокер) снимает это автоматически.
- **Существование файлов сертификата не проверяется в `validate`.** [`config.go#L274`](../internal/config/config.go#L274) сверяет только «оба или ни одного». Опечатка в пути даёт `log.Fatalf` из горутины [`serve`](../cmd/dbbridge/main.go#L252) уже после того, как остальные листенеры подняты, метастор подключён и пулы открыты, а `defer`-очистки при `log.Fatalf` не выполняются. Дешевле сделать `tls.LoadX509KeyPair` до старта листенеров и упасть с внятной ошибкой.
- **Переменная `tls` затеняет имя стандартного пакета.** [`main.go#L237`](../cmd/dbbridge/main.go#L237). Сейчас компилируется, потому что `crypto/tls` не импортирован, но любая правка по предыдущим двум пунктам потребует переименования. `tlsCfg` был бы точнее.
- **Нет тестов на TLS-часть.** [`config_test.go`](../internal/config/config_test.go#L130) покрывает только подстановку. Новое правило валидации «cert без key - ошибка» и `TLSConfig.Enabled()` не покрыты ничем, хотя это два маленьких табличных случая. В описании PR раздел «Verification» перечисляет только тесты подстановки, так что заявка и покрытие сходятся, но пробел стоит закрыть.
- **MinIO в compose остался с `minioadmin/minioadmin` и опубликованным API.** [`docker-compose.yaml#L38`](../deploy/docker-compose.yaml#L38). Бакет закрыли от анонима, но root-креды общеизвестны и порт 9000 торчит на хосте, так что содержимое по-прежнему читается одной командой `mc alias set`. Логично сделать как с Redis: `MINIO_ROOT_USER: ${MINIO_ROOT_USER:-minioadmin}` и те же переменные в `minio-init` и в `S3_ACCESS_KEY_ID`.
- **`S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` захардкожены прямо в compose** ([`docker-compose.yaml#L70`](../deploy/docker-compose.yaml#L70)), в отличие от `REDIS_PASSWORD` и токенов, которые получили `${VAR:-default}`. Расхождение в стиле внутри одного файла.
- **`expose: "6379"`** ([`docker-compose.yaml#L9`](../deploy/docker-compose.yaml#L9)) - декоративный ключ, ничего не ограничивающий: контейнеры одной сети и так видят все порты друг друга. Реальную защиту дало удаление `ports`, а комментарий выше читается так, будто работает `expose`.
- **Нет `.dockerignore`.** `COPY . .` в builder-стейдже тащит `.git`, локальный `results/` и любые локальные конфиги в build-контекст. В финальный образ они не попадают (multi-stage, копируется только бинарь), так что это про размер контекста и про кэш builder-слоя, а не про утечку в published-образ. Для PR про «секреты не в образе» файл напрашивается.
- **`automountServiceAccountToken: false`** просится в тот же набор в [`deployment.yaml#L24`](../deploy/k8s/deployment.yaml#L24): capabilities сброшены, seccomp выставлен, а токен SA по-прежнему монтируется, хотя приложение в API кластера не ходит.
- **Пример reload в README указывает не тот порт.** [`deploy/README.md#L136`](../deploy/README.md#L136) показывает `http://localhost:8080/v1/admin/reload`, но во всех трёх поставляемых конфигах с `admin_addr` этот роут живёт на 8081 (и на 8181 снаружи compose). Строка выше это оговаривает словами, но команду скопируют как есть.
- **Расхождение набора ключей между эталонными конфигами.** [`dbbridge-blue.yaml`](../deploy/configs/dbbridge-blue.yaml#L11) и green не задают `trusted_proxy_count`, хотя [`configs/dbbridge.yaml`](../configs/dbbridge.yaml#L23) и ConfigMap задают. Дефолт 0 для compose верный, но три «образцовых» конфига проще держать структурно одинаковыми.
- **`/app/results` в образе не используется в k8s.** [`Dockerfile#L34`](../deploy/Dockerfile#L34) создаёт и chown-ит каталог, а ConfigMap указывает `/data/results`. Для compose каталог нужен, для k8s это мёртвый слой; стоит хотя бы одной строкой пояснить, что путь - под compose.

## Что проверено и выглядит корректно

- **securityContext согласован с тем, что процесс реально пишет.** [`main.go#L84`](../cmd/dbbridge/main.go#L84) создаёт FS-store (и делает `MkdirAll`) при непустом `storage.fs.root` даже когда `default_storage: s3`; ConfigMap ставит `root: /data/results`, deployment монтирует туда `emptyDir`, `fsGroup: 10001` делает том доступным на запись группе процесса. Под `readOnlyRootFilesystem: true` стартовать есть куда. `/tmp` в проде не используется (`os.CreateTemp` встречается только в `internal/testutil`), но смонтирован на всякий случай - это дёшево и безопасно.
- **Диагноз issue #5 верен.** Kubernetes разворачивает `$(VAR)` только в `env`, `command` и `args`, но не в `data` ConfigMap, так что `dbbridge-$(POD_NAME)` действительно оставался литералом и обе реплики считали себя одним владельцем. Подстановка на стороне приложения - правильное место для фикса.
- **Ошибка на неустановленной переменной вместо пустой строки** ([`config.go#L186`](../internal/config/config.go#L186)) - осознанный fail-closed: пустая подстановка воспроизвела бы ровно тот же баг с одинаковыми ID. Голый `$VAR` не трогается, и это покрыто тестом ([`config_test.go#L141`](../internal/config/config_test.go#L141)).
- **Логика h2c.** Предупреждение печатается только когда TLS выключен и `allow_h2c` не выставлен; при включённом TLS ставится `SetHTTP2` и HTTP/2 приезжает через ALPN, `SetUnencryptedHTTP2` не включается. Валидация требует пару cert+key, `Enabled()` требует оба - несогласованного состояния «сертификат есть, ключа нет» не возникает.
- **Секреты не утекают в наблюдаемые поверхности.** Отчёт reload отдаёт только идентификаторы баз ([`manager.go#L280`](../internal/core/manager/manager.go#L280) через `dbIDs`), в лог `main.go` уходят те же идентификаторы; `/metrics` конфиг не дампит; финальный слой образа содержит только бинарь. Redis-адрес логируется без пароля.
- **Перенос `/metrics` на admin-листенер согласован во всех артефактах**: `admin_addr: ":8081"` в трёх конфигах, порт `admin` в deployment, аннотация `prometheus.io/port: "8081"`, `prometheus.yml` на `:8081`, порты 8181/8182 в compose, Makefile и README. Скрейп без токена работает, потому что `/metrics` смонтирован без `require(ScopeAdmin)` ([`rest/server.go#L156`](../internal/transport/rest/server.go#L156)) - это существующее поведение, PR его не менял. Стоит держать в голове, что в compose админ-порт опубликован на хост, то есть `/metrics` там читается анонимно; для dev-стека приемлемо.
- **Снятие публикации порта Redis не ломает тесты.** Интеграционные тесты поднимают собственные контейнеры через testcontainers и на compose-стек не завязаны - в Go-коде нет ни одной ссылки на `localhost:6379`.
- **Конвенции соблюдены**: заголовок коммита в формате `type(scope): subject`, ветка с префиксом `chore/`, ссылок на внутренние планировочные документы в описании PR нет.
- `go build ./...`, `go vet ./...`, `gofmt -l .`, `go test ./internal/config/... ./internal/transport/...` - чисто.
