## Важное

### `TestRedis_HeartbeatKeepsTerminalWrites` прошёл бы на баге, ради которой написан

[`integration_test.go`](../test/integration/integration_test.go#L317)

Комментарий обещает: «регрессия на lost update, который заставил вынести lease в
отдельные ключи: heartbeat **параллельно** с терминальной записью не должен
восстанавливать RUNNING». Параллельности в тесте нет - это три последовательных шага:
50 синхронных `Heartbeat` ([L339](../test/integration/integration_test.go#L339)),
затем `PutQuery` терминальной записи
([L349](../test/integration/integration_test.go#L349)), затем ещё 50 `Heartbeat`
([L353](../test/integration/integration_test.go#L353)).

Проверено по старой реализации (`git show 672d6e2^:internal/state/redis.go`), где
`Heartbeat` делал read-modify-write записи:

```
for 50: GetQuery(q1) -> RUNNING; rec.LeaseDeadline = deadline; UpdateQuery(RUNNING)
PutQuery(SUCCEEDED + Result)   -> SRem из instance-сета
for 50: GetQuery(q1) -> SUCCEEDED; rec.LeaseDeadline = deadline; UpdateQuery(SUCCEEDED)
```

Итог на баговом коде: `State == SUCCEEDED`, `Result != nil`, `CountInFlight == 0` - то
есть все три ассерта теста зелёные. Баг требует интерливинга (heartbeat прочитал
RUNNING → приземлилась терминальная запись → heartbeat записал RUNNING обратно), а
последовательный прогон его воспроизвести не может в принципе.

К тому же это дубль: [`internal/state/redis_test.go`](../internal/state/redis_test.go#L39)
уже содержит `TestRedisHeartbeatDoesNotRewriteRecord`, который на miniredis сравнивает
байты записи до и после heartbeat - куда более строгая формулировка того же инварианта.

Исправление: либо сделать тест действительно конкурентным (goroutine, гоняющая
`Heartbeat` в цикле, пока другая пишет терминальное состояние, N итераций, ассерт что
терминальное состояние выжило - и прогонять его под `-race`), либо честно переименовать
в «heartbeat не трогает запись против реального Redis» и убрать слово «concurrent» из
комментария.

### `TestS3_ResultRoundTrip` не прогоняет multipart uploader, хотя это заявлено как его смысл

[`integration_test.go`](../test/integration/integration_test.go#L128)

Комментарий: «материализует в MinIO, единственный путь, который прогоняет multipart
uploader и контракт Close-waits-for-upload, на котором держится I4». Описание PR
повторяет то же про «S3 multipart uploader».

`S3ResultStore` использует
[`manager.NewUploader(s3Client)`](../internal/storage/backends/s3/storage.go#L48) с
дефолтами: `PartSize` = 5 MiB. Для не-seekable тела (здесь `io.Pipe`) uploader читает
первую часть в буфер и, если достиг EOF внутри неё, отправляет обычный `PutObject`.
Тест грузит результат `SELECT id, name FROM users` - две строки JSONL, порядка 60 байт.
Multipart-путь (`CreateMultipartUpload` / `UploadPart` / `CompleteMultipartUpload`) не
выполняется ни разу.

Вход → неверный результат: если сломать сборку частей или завершение multipart-загрузки,
тест останется зелёным.

Контракт Close-waits-for-upload при этом действительно проверяется: `Mode: "sync"`,
затем `readResult` сразу читает объект.

Исправление: добавить один запрос, который заведомо перевалит за 5 MiB, например
`SELECT g, repeat('x', 200) FROM generate_series(1, 40000) g`, и на нём проверять
`Stat().SizeBytes` против `rec.Result.SizeBytes`. Либо убрать упоминание multipart из
комментария и из описания PR.

### `TestRedis_GCRunsOnce` не запускает GC и дублирует существующий unit-тест

[`integration_test.go`](../test/integration/integration_test.go#L376)

Комментарий: «проверяет, что кластерный лок не даёт двум инстансам гоняться за одними и
теми же истёкшими записями». Фактически тест создаёт **один** `RedisMetaStore` и дважды
вызывает `TryLock(ctx, "gc", 30*time.Second)`. Ни второго инстанса, ни `QueryManager`,
ни `collectGarbage()`, ни просроченных записей в тесте нет - это проверка семантики
`SETNX`, а не GC.

Ровно это уже проверяет
[`TestRedisTryLock`](../internal/state/redis_test.go#L244) на miniredis.

Вход → неверный результат: если `collectGarbage` перестанет брать лок (например, при
рефакторинге `TryLock` вынесут наверх и потеряют), тест этого не заметит.

Исправление: поднять два харнесса на одном Redis, положить просроченную терминальную
запись (`FinishedAt` в прошлом, `ResultTTL` маленький) и проверить, что запись удалена
ровно один раз и в логах нет ошибок удаления; либо переименовать тест в
`TestRedis_TryLockIsExclusive` и убрать про GC из комментария.

### Спецификация утверждает обязательную аутентификацию, код и README из этого же PR - обратное

[`spec.md`](spec.md#L178), [`README.md`](../README.md#L72)

Новый раздел спеки: «Every `/v1` route and every gRPC procedure **requires** a
credential». README, изменённый тем же коммитом: «`/v1` routes require a bearer token
**when `auth.tokens` is configured**».

По коду прав README:

- [`main.go#L159`](../cmd/dbbridge/main.go#L159): `authenticator` строится только при
  `cfg.Auth != nil`, иначе остаётся `nil`.
- [`rest/server.go#L97`](../internal/transport/rest/server.go#L97): `require(scope)` при
  `Auth == nil` возвращает pass-through middleware; на старте пишется
  `WARNING: no auth tokens configured, the API accepts unauthenticated requests`.
- [`config.go#L271`](../internal/config/config.go#L271): ошибка старта только для
  «`auth:` есть, но `tokens` пуст». Полное отсутствие секции - штатный режим.
- `configs/dbbridge.yaml` секцию `auth:` держит закомментированной.

Вход → неверный результат: оператор читает спеку, разворачивает конфиг без `auth:` и
получает открытый API, исполняющий SQL под сервисными кредами всех БД - при том, что
нормативный документ обещал обязательный credential.

Исправление: привести спеку к коду («credential требуется, когда сконфигурирован
`auth.tokens`; без секции API открыт и это логируется предупреждением») либо, если
обязательность и есть замысел, отдельным PR сделать отсутствие `auth` фатальным. Сейчас
два документа из одного коммита противоречат друг другу.

## Мелочи и предложения

### `go run …@latest` в `make vulncheck` делает CI невоспроизводимым

[`Makefile`](../Makefile#L72): `go run golang.org/x/vuln/cmd/govulncheck@latest ./...`.
Версия инструмента резолвится на каждом прогоне, поэтому релиз govulncheck может
уронить CI без единого изменения в коде, а `make ci` (в котором `vulncheck` теперь
последним шагом) требует сети. Плюс `@latest` - это неподписанный исполняемый код,
который запускается в CI. Предложение: закрепить версию (`@v1.1.x`) или, что чище на
Go 1.26, добавить как `tool`-зависимость через `go get -tool` и вызывать `go tool
govulncheck`.

### `seed()` игнорирует `RowStream.Err()`

[`suite_test.go#L166`](../test/integration/suite_test.go#L166). Цикл
`for rows.Next() {}` и `rows.Close()` есть, `rows.Err()` не проверяется - при том что
интерфейс `db.RowStream` объявляет `Err()` именно потому, что драйверы откладывают
ошибку, и продакшн-путь её проверяет
([`encoder.go#L144`](../internal/storage/encoder.go#L144)). Для pgx v5 `pool.Query`
возвращает часть серверных ошибок отложенно. Вход → неверный результат: упавший
`CREATE TABLE` проходит молча, а тест падает позже и непонятно - «rows_read = 0, want 2».
Исправление: добавить `if err := rows.Err(); err != nil { t.Fatalf(...) }` перед
`rows.Close()`.

### `pollTerminal` теряет причину отказа

[`integration_test.go#L21`](../test/integration/integration_test.go#L21):
`if err == nil && rec.State.IsTerminal()`. Если `GetQueryStatus` стабильно возвращает
ошибку (запись удалили, Redis отвалился), цикл крутится до дедлайна и сообщает «query
… did not reach a terminal state within 30s», пряча настоящую причину. Предложение:
запоминать последнюю ошибку и печатать её в `t.Fatalf`.

### `test/integration` не покрыт ни `go vet`, ни `golangci-lint`

Проверено экспериментом: пакет, у которого все файлы отсечены build-тегом, шаблоном
`./...` пропускается молча, без ошибки. Значит `make vet`, `make lint` и `make test-all`
новые 765 строк не видят; компиляция ловится только джобой `containers`. `gofmt -l .`
их покрывает, потому что ходит по файлам. Предложение: добавить в быструю джобу дешёвый
`go vet -tags=integration ./test/integration/...` (Docker для этого не нужен) и/или
`--build-tags=integration` в конфиг golangci-lint.

### Комментарий в `Makefile` и строка в `AGENTS.md` про `make ci` больше не полны

[`Makefile#L90`](../Makefile#L90) «The CI workflow runs these same targets, one per
step» и [`AGENTS.md#L29`](../AGENTS.md#L29) «`make ci` - everything CI runs». Начиная с
этого PR workflow запускает ещё и `make test-containers` в отдельной джобе, а `ci:`
([Makefile#L91](../Makefile#L91)) его не включает. Сюда же: раздел Verification в
описании PR ссылается на «`make ci` in full - green», что по построению не покрывает
новый контейнерный набор, то есть в описании нет утверждения, что новые тесты
запускались.

### Глобальная регистрация `s3` переживает контейнер MinIO

[`integration_test.go#L141`](../test/integration/integration_test.go#L141):
`storage.Register("s3", store)` пишет в глобальный реестр процесса, а MinIO
терминируется по `t.Cleanup` этого теста. Снять регистрацию нельзя - API реестра
предоставляет только `Register`, который паникует на дубликате. Сейчас безопасно,
потому что ни один тест после `TestS3_ResultRoundTrip` к бэкенду `s3` не обращается, но
любой новый тест ниже по файлу получит «мёртвый» стор с указателем на погашенный порт.
Предложение: вынести MinIO и регистрацию `s3` в `TestMain` рядом с `fs`, раз реестр всё
равно на весь бинарь.

### Теги образов не запиннены (кроме MinIO)

[`suite_test.go`](../test/integration/suite_test.go#L87): `redis:7-alpine`,
`postgres:18-alpine`, `mysql:8.4` - плавающие теги; `minio/minio:RELEASE.2025-09-07T16-13-09Z`
запиннен. С dev-стеком (`deploy/docker-compose.yaml`) redis, postgres и minio совпадают,
и это хорошо. Для CI, где расхождение образа и кода надо уметь отличать, стоит либо
пиннить дайджестом везде, либо явно задокументировать, что плавающие теги здесь
осознанный выбор.

### MySQL стартует без явного `WithStartupTimeout`, в отличие от PostgreSQL

[`suite_test.go#L143`](../test/integration/suite_test.go#L143) полагается на дефолтную
wait-стратегию модуля (60 с), тогда как PostgreSQL получил явные две минуты
([L113](../test/integration/suite_test.go#L113)). Холодная инициализация MySQL 8.4 на
загруженном ранере GitHub - классический источник флейков. Предложение: выдать MySQL
такой же явный таймаут.

### Контейнерная джоба идёт без `-race`

[`ci.yml#L53`](../.github/workflows/ci.yml#L53) запускает `make test-containers` без
детектора гонок, хотя новые тесты трогают ровно те конкурентные пути (heartbeat-воркер,
reaper, GC, pub/sub-вотчеры), ради которых `-race` и нужен. Предложение: добавить
`-race` в `test-containers` или отдельным шагом.

### `heartbeat_ttl: 1s` оставляет запас в 500 мс

[`suite_test.go#L280`](../test/integration/suite_test.go#L280). При TTL 1 с
heartbeat-воркер тикает раз в 500 мс
([`manager.go#L982`](../internal/core/manager/manager.go#L982)), а чужой reaper - раз в
секунду ([`manager.go#L1174`](../internal/core/manager/manager.go#L1174)). Задержка
воркера больше 500 мс роняет lease, и в `TestRedis_MultiNode` долгий запрос может уйти
в `FAILED/OWNER_LOST` вместо ожидаемого `CANCELED`. Практический риск низкий: грейс в
2 с от `CreatedAt` закрывает старт, а `StopQuery` посылается почти сразу. Но 2-3 с дали
бы такой же по смыслу тест с заметно большим запасом.

### Ассерт про «done-1 пережил тот же проход» не может упасть

[`integration_test.go#L275`](../test/integration/integration_test.go#L275). Комментарий
говорит «терминальная запись должна пережить тот же проход», но reaper её вообще не
видит: `ListStaleQueries` фильтрует по `PENDING`/`RUNNING`
([`redis.go#L410`](../internal/state/redis.go#L410)), а GC требует
`now > FinishedAt + ResultTTL` ([`redis.go#L385`](../internal/state/redis.go#L385)) - в
тесте `FinishedAt = time.Now()`, `ResultTTL = 1h`, и первый тик GC вообще наступает
через минуту (`gcInterval = time.Minute`), то есть за пределами 30-секундного дедлайна
теста. Как чёрный ящик проверка фильтра осмысленна, но формулировку «тот же проход»
стоит поправить.

### testcontainers тянет ~40 модулей в основной граф зависимостей

[`go.mod`](../go.mod) прибавляет docker/moby-клиент, `logrus`, `gopsutil`, `testify`,
`go-winio` и прочее в `require` основного модуля. Для приложения это обычная практика, и
`govulncheck ./...` их не сканирует (пакет отсечён тегом), но обратная сторона та же:
будущая уязвимость в `moby/moby/client` не будет поймана, а `go install` тянет лишнее.
Отдельный `go.mod` в `test/integration` (или `go.work`) - вариант, если граф основного
модуля важно держать чистым; иначе достаточно решения «принято осознанно».

### `go 1.26.6` вместо директивы `toolchain`

[`go.mod#L3`](../go.mod#L3). Патч-версия в директиве `go` поднимает не только требуемый
тулчейн, но и языковую версию модуля. Штатный способ выразить «собирать не ниже
1.26.6», не трогая языковой уровень, - оставить `go 1.26.0` и добавить
`toolchain go1.26.6`. На `setup-go` с `go-version-file: go.mod` результат в CI будет тот
же, так что это вопрос точности выражения намерения.

## Что проверено и выглядит корректно

- **Изоляция build-тегом работает.** Проверено на минимальном модуле: каталог, все файлы
  которого отсечены тегом, шаблонами `go build ./...`, `go test ./...`, `go vet ./...`
  пропускается молча, без ошибки. `make test`, `make test-all`, `make test-race` и
  `make ci` Docker не требуют.
- **Отсутствие Docker роняет тест, а не скипает его.** В пакете нет ни одного `t.Skip`;
  ошибка `tcredis.Run` уходит в `t.Fatalf`. Для отдельной CI-джобы это правильное
  поведение - «зелёный молча пропущенный набор» невозможен.
- **Порядок cleanup верный.** `t.Cleanup` выполняется LIFO, и регистрация идёт
  контейнер → metastore → manager, поэтому фактический порядок закрытия
  `qm.Close()` → `redisStore.Close()` → `container.Terminate()`. Обратный порядок дал бы
  ошибки «connection refused» в фоновых воркерах на выходе.
- **Кросс-тестовой связности нет.** Каждый тест поднимает свой Redis, поэтому ключи не
  протекают между тестами; `t.Parallel()` нигде не вызывается, набор строго
  последовательный.
- **`TestMySQL_EndToEnd` действительно проверяет маппинг типов.** MySQL отдаёт `varchar`
  как `[]byte`, и без нормализации в
  [`encoder.go`](../internal/storage/encoder.go#L110) `encoding/json` записал бы
  base64; ассерт `rows[0]["name"] != "alice"` это ловит.
- **`TestRedis_ReadOnlyGuard` бьёт по настоящей БД.** Guard стоит в
  [`manager.go#L356`](../internal/core/manager/manager.go#L356), то есть на пути
  `svc.StartQuery`, который тест и вызывает; после отклонённого `DELETE` проверяется,
  что `count(*)` всё ещё 2. `seed()` идёт мимо guard напрямую через `db.OpenPool`, что
  корректно.
- **`TestRedis_OwnerLost` проходит через настоящий `UpdateQueryIfState`** (`WATCH`/`MULTI`
  в Redis) и через реальное истечение lease-ключа - это то новое покрытие, которое
  miniredis-тесты дают лишь в эмуляции.
- **`TestRedis_MultiNode` прогоняет Lua-скрипт идемпотентности и pub/sub** между двумя
  процессными инстансами на одном Redis - тоже настоящий новый путь.
