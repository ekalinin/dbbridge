# Код-ревью PR #15: feat(storage): implement parquet, register clickhouse, checksum results

Дата: 2026-08-17. Ветка `feat/storage-formats` → `feat/transport-auth`, коммит `5dfb02e36ecc6109dd0275e173e0ff8ede4113eb`.

Ревью охватывает только `origin/feat/transport-auth..origin/feat/storage-formats`
(13 файлов, +620/-16). PR пятый в стеке; находки, приходящие из более ранних веток,
не включены.

Все находки, помеченные как подтверждённые, проверены запуском кода на копии worktree
(`/tmp/pq-probe`, отдельный от ревью-worktree). Копия удалена.

## Что делает PR

- [`parquet.go`](../internal/storage/parquet.go) - настоящий энкодер Parquet на
  `parquet-go v0.32.0`. Первые 128 строк буферизуются, чтобы вывести тип каждой колонки
  (Parquet требует схему заранее, а `RowStream` отдаёт только имена), дальше поток пишется
  построчно. Колонка с расходящимися типами в выборке откатывается к тексту, SQL NULL
  проходит через optional-поля.
- [`encoder.go`](../internal/storage/encoder.go#L77) - ветка `parquet` больше не падает
  в JSONL; `jsonl` выделена в отдельный case.
- [`main.go`](../cmd/dbbridge/main.go#L114) - бэкенд ClickHouse наконец регистрируется и
  закрывается на shutdown; FS-стор создаётся только если конфиг его просит;
  недоступный `default_storage` валит старт.
- [`config.go`](../internal/config/config.go#L181) - `default_storage` проверяется на
  этапе загрузки конфига, а не после первого запроса.
- [`manager.go`](../internal/core/manager/manager.go#L633) - `ResultRef.Checksum`
  считается через `io.MultiWriter` на тех же байтах, что идут в хранилище.
- `ValidResultFormats` пополнен `parquet`; тесты, которые использовали `parquet` как
  заведомо невалидный формат, перенацелены на `avro`.

## Итог

Направление правильное, и три вещи сделаны аккуратно: checksum действительно совпадает
с байтами в хранилище для `fs` и `s3` и стоит ровно в одном проходе; ранняя валидация
`default_storage` закрывает реальную дыру; per-query override `storage_backend` уже
проверялся по живому реестру в [`manager.go`](../internal/core/manager/manager.go#L339),
так что заявленная цель «не падать после выполненного SQL» для него выполняется.

Но сам энкодер Parquet имеет три проблемы, каждая из которых воспроизводится запуском.
Одна из них - паника, гасящая процесс, и триггерится она обычным `SELECT`, который
вправе прислать любой авторизованный клиент. Вторая - весь результат целиком лежит
в памяти до `Close`, что прямо противоположно тому, что утверждает описание PR
(«everything past the sample is streamed, so the buffer stays bounded»). Третья -
комбинация `result_format: parquet` + `storage_backend: clickhouse`, которую этот PR
делает достижимой впервые, гарантированно даёт нечитаемый файл.

Блокеров - 3, важного - 5, мелочей - 10.

## Блокеры

### Коллизия имён колонок роняет процесс

[`parquet.go`](../internal/storage/parquet.go#L120), [`parquet.go`](../internal/storage/parquet.go#L73)

`uniqueColumnNames` не кладёт сгенерированное имя обратно в `seen`, поэтому суффикс
может столкнуться с настоящей колонкой:

```
["a", "a", "a_1"]   -> ["a", "a_1", "a_1"]
["a", "a_1", "a"]   -> ["a", "a_1", "a_1"]
```

Дальше [`buildParquetSchema`](../internal/storage/parquet.go#L166) кладёт имена в
`parquet.Group` (это map), два одинаковых ключа схлопываются в одно поле, схема получает
на одно поле меньше, чем колонок. `cols[1].index == cols[2].index`, и `parquet.Row`
длиной 3 содержит два соседних значения с одинаковым column index. `Row.Range` в
parquet-go группирует значения по соседству и назначает группам индексы 0, 1, 2
подряд, после чего `rg.values[columnIndex]` выходит за границы среза колонок.

Сценарий отказа (проверен запуском `EncodeStream` на реальном коде):

```
POST /v1/queries {"sql":"SELECT 1 AS a, 2 AS a, 3 AS a_1",
                  "options":{"result_format":"parquet"}}

panic: runtime error: index out of range [2] with length 2
```

`ReadOnly` из [`sqlguard`](../internal/sqlguard/sqlguard.go#L44) такой запрос
пропускает - это обычный `SELECT`. `qm.run` запускается через
[`qm.queryWG.Go`](../internal/core/manager/manager.go#L457), `sync.WaitGroup.Go` панику
не перехватывает, и `recover()` в непроверочном коде репозитория нет ни одного
(`grep -rn "recover()" internal cmd --include='*.go'` - пусто). Паника гасит весь
процесс: инстанс теряет все свои in-flight запросы, обход drain и I5, а запросы в
`RUNNING` по §3 спеки уедут в `FAILED (owner_lost)`. То есть это ещё и remote DoS
одним запросом от любого клиента со скоупом `write`.

Исправление: складывать сгенерированное имя в `seen` и повторять суффикс до
уникальности; отдельно проверять `len(schema.Fields()) == len(names)` и возвращать
ошибку, а не собирать заведомо битую `Row` - схема, не совпадающая по размеру с набором
колонок, это баг, который лучше видеть как ошибку запроса, чем как панику.

### Весь результат parquet держится в памяти до Close

[`parquet.go`](../internal/storage/parquet.go#L63)

`parquet.NewGenericWriter` берётся с дефолтным конфигом, а в нём
`DefaultMaxRowsPerRowGroup = math.MaxInt64` и `ColumnPageBuffers = memoryBufferPool`.
Row group не флашится никогда, пока не вызван `Close`, а страницы копятся в буферах
в куче. В нижележащий `io.Writer` до `Close` не уходит ни байта.

Измерено на реальном коде:

```
200 000 строк x ~1 KB   -> 203 366 916 байт результата, пик кучи 253 MiB
100 000 строк x ~1 KB   -> в writer до Close записано 0 байт
```

Второй замер сделан так: `Next()` помечает счётчик записанных байт в момент, когда
поток закончился, то есть непосредственно перед `writer.Close()`. Ноль.

Отсюда три следствия:

1. Результат в N гигабайт требует N гигабайт RSS. При `max_concurrent_queries > 1`
   это умножается на число одновременных parquet-запросов. Размер результата задаёт
   клиент своим SQL - это OOM по запросу.
2. Нарушен §5.2 спеки («Each returns a stream so that large results are not kept in
   memory») и дух I4 (stream+persist во время выполнения). CSV и JSONL это свойство
   держат, parquet его теряет.
3. Для S3 весь объект уезжает одним куском внутри `writer.Close()`, а не пока идёт
   выполнение; `StorageWriteDuration` перестаёт отражать перекрытие с чтением из БД.

Описание PR утверждает обратное - это стоит либо починить, либо переписать в описании.

Исправление: передать опции писателю, например
`parquet.NewGenericWriter[any](cw, schema, parquet.MaxRowsPerRowGroup(N))` с N порядка
десятков-сотен тысяч (row group флашится в выходной поток по достижении лимита),
либо `parquet.ColumnPageBuffers(parquet.NewFileBufferPool(dir, "dbbridge-*"))`, чтобы
буферы уходили на диск. Первый вариант дешевле и даёт настоящий стриминг.

### parquet поверх бэкенда clickhouse даёт нечитаемый файл

[`clickhouse/storage.go`](../internal/storage/backends/clickhouse/storage.go#L79),
[`clickhouse/storage.go`](../internal/storage/backends/clickhouse/storage.go#L219)

ClickHouse-стор строчно-ориентированный: `Writer` режет входящий поток
`bufio.Scanner` и пишет по строке в колонку `data`, `Reader` склеивает их обратно
через `line + "\n"`. Для JSONL и CSV это байт-в-байт обратимо. Для parquet - нет.

До этого PR комбинация была недостижима: `parquet` отвергался валидацией, а бэкенд
`clickhouse` не был зарегистрирован в `main.go`. Этот PR включает обе половины и
никак их не разводит - `QueryOptions.Validate` проверяет формат и бэкенд по
отдельности, кросс-проверки нет.

Сценарий отказа (проверен: логика round trip воспроизведена локально поверх реального
вывода `EncodeStream`):

```
POST /v1/queries {"sql":"SELECT ...",
                  "options":{"result_format":"parquet","storage_backend":"clickhouse"}}
```

```
исходный файл 24885 байт -> после round trip 24886 байт
parquet.OpenFile: invalid magic footer of parquet file: "AR1\n"
```

Механизм: parquet не заканчивается на `\n`, а `Reader` дописывает `\n` после каждой
строки, включая последнюю. Читатель ищет `PAR1` в последних четырёх байтах и находит
`AR1\n`. Плюс два усугубляющих фактора, менее детерминированных: `bufio.ScanLines`
срезает `\r` перед `\n`, так что любая последовательность `\r\n` внутри бинарника
теряет байт; и `scanner.Buffer(buf, 10*1024*1024)` уронит запись с
`token too long`, если в потоке встретится участок длиннее 10 MB без `\n`.

Побочно ломается и обещание нового `Checksum`: он считается по байтам,
ушедшим в писатель, а `Reader` возвращает другие байты, так что для этой пары
формат/бэкенд `sha256:` в статусе будет заведомо не совпадать со скачанным.

Исправление: либо отвергать пару `parquet` + `clickhouse` в
[`QueryOptions.Validate`](../internal/core/domain/models.go#L71) (нужен доступ к
бэкенду, он там уже нормализован в `SubmitQuery`), либо хранить в ClickHouse
бинарные чанки фиксированного размера вместо строк. Второе правильнее, но это
отдельная работа - для этого PR достаточно закрыть комбинацию.

## Важное

### Значение с типом, разошедшимся со схемой после выборки, молча становится NULL

[`parquet.go`](../internal/storage/parquet.go#L222)

Тип колонки решается по первым 128 строкам. Дальше конвертер жёсткий: если
`toInt64` / `toFloat64` / приведение к `bool` / `time.Time` не сработали, возвращается
`parquet.NullValue()`. Ошибки нет, счётчик строк не меняется, запрос завершается
`SUCCEEDED`.

Сценарий отказа (проверен запуском):

```
колонка n: 128 строк int64, затем "not-a-number", затем 3.5
-> файл открывается, 130 строк, последние две значения = null
```

Реалистичные источники расхождения: колонка, у которой в первых 128 строках только
NULL, а дальше числа (тогда `decided[i]` остаётся false, тип - строка, и числа
уедут в текст - это ещё терпимо); колонка `int64` в выборке и `float64` дальше
(driver вернул другой тип для другой партиции); `time.Time` в выборке и строка дальше.
Во всех этих случаях клиент получает файл, который открывается и выглядит валидным,
но с потерянными значениями. Для прокси, который «материализует результат ровно
один раз» (I4), молчаливая потеря данных хуже, чем провал запроса.

Исправление: в конвертере, когда приведение не удалось, а значение не nil,
возвращать ошибку вместо NULL - `converterFor` придётся сменить сигнатуру на
`func(any) (parquet.Value, error)`. Как минимум - логировать и считать в
`QueryStats`, чтобы это не было невидимым.

### uint64 больше MaxInt64 записывается отрицательным

[`parquet.go`](../internal/storage/parquet.go#L282)

`kindOf` относит `uint64` к `kindInt`, `nodeFor` даёт `parquet.Int(64)` -
знаковый INT64, `toInt64` делает `int64(n)` без проверки.

Сценарий отказа (проверен запуском): `uint64(1<<63)` сохраняется как
`-9223372036854775808`. Это ровно то, что вернёт MySQL для `BIGINT UNSIGNED`
и ClickHouse для `UInt64` - типы не экзотические.

Исправление: либо `parquet.Uint(64)` для колонок, у которых в выборке встретились
беззнаковые значения, либо откат такой колонки к тексту.

В описании PR перечислены четыре свойства энкодера. Тестами закрыты два:

Не покрыты также: колонка, целиком NULL в выборке; ошибка `writer.Close()`;

непокрытая ветка дублей имён и содержит панику из первого блокера -

Исправление: добавить кейс `["a","a","a_1"]` в `TestUniqueColumnNames`

### Реестр хранилищ не переживает hot-reload

[`main.go`](../cmd/dbbridge/main.go#L135), [`config.go`](../internal/config/config.go#L181)

Новая проверка `validate()` смотрит только на наличие секции конфига, а
`storage.GetStore(cfg.Instance.DefaultStorage)` в `main.go` выполняется один раз
на старте. Реестр после старта не пополняется вообще.

Сценарий отказа: инстанс поднят с `default_storage: fs` и без секции
`storage.clickhouse`. Оператор дописывает DSN и `default_storage: clickhouse`,
шлёт SIGHUP. `validate()` проходит (DSN есть), конфиг подменяется, стор никто не
строил - и каждый последующий запрос получает 400 `unknown storage backend "clickhouse"`
на [`manager.go`](../internal/core/manager/manager.go#L339). Реестр не восстановить
ничем, кроме рестарта, а PR-описание при этом обещает ловить такое «at config load».

Исправление: либо проверять `storage.GetStore` в `QueryManager.Reload` и отвергать
reload целиком, либо честно записать в `NonReloadableChanges`, что `default_storage`
и секция `storage` не перезагружаются.

### Инициализация ClickHouse-стора падает предупреждением, а FS - фатально

[`main.go`](../cmd/dbbridge/main.go#L117)

Три бэкенда обрабатываются тремя разными способами: FS - `log.Fatalf`, S3 -
`log.Printf("WARNING")`, ClickHouse - тоже WARNING. При этом
`NewClickHouseResultStore` делает `CREATE TABLE IF NOT EXISTS` и `sql.Open`, то есть
может не подняться из-за недоступности ClickHouse в момент старта.

Сценарий: `default_storage: fs`, `storage.clickhouse.dsn` задан, ClickHouse в
момент старта лежит. Процесс поднимается, в логе одна строка WARNING, а запросы
с `storage_backend: clickhouse` весь срок жизни процесса отвечают 400 - даже
после того, как ClickHouse вернулся. Проверка `GetStore(DefaultStorage)` этого
не ловит, потому что дефолт другой.

Исправление: как минимум привести к одному правилу - если секция бэкенда задана,
неудача его построения фатальна. Иначе получается «конфиг просит бэкенд, процесс
молча стартует без него».

## Мелочи и предложения

### Мёртвая compile-time проверка

[`parquet.go`](../internal/storage/parquet.go#L300)

`var _ io.Writer = (*CountingWriter)(nil)` ничего не утверждает: `CountingWriter`
уже передаётся как `io.Writer` в [`encoder.go`](../internal/storage/encoder.go#L34)
и в `parquet.NewGenericWriter`. Убрать вместе с импортом `io`.

### `writer.Close()` не вызывается на путях ошибок

[`parquet.go`](../internal/storage/parquet.go#L104)

Все пять ранних `return` пропускают `Close`. parquet-go возвращает страничные
буферы в пул именно в `Close`, так что буферы row group остаются висеть до GC -
а по второму блокеру это может быть весь результат. Просится
`defer` с флагом, чтобы не было двойного закрытия.

### Бинарные данные помечаются логическим типом STRING

[`parquet.go`](../internal/storage/parquet.go#L199)

`[]byte` попадает в `kindString` и пишется как `parquet.String()`, то есть
BYTE_ARRAY с логическим типом STRING (UTF-8). Байты round trip проходят
(проверено запуском на `[]byte{0x00,0xff,0xfe,'a',0x0d,0x0a}`), но Arrow, Spark и
DuckDB вправе отвергнуть или испортить невалидный UTF-8 в STRING-колонке.
Для `bytea` / `BLOB` уместнее `parquet.Leaf(parquet.ByteArrayType)` без
логического типа.

### Наносекунды в timestamp срезаются

[`parquet.go`](../internal/storage/parquet.go#L250)

`t.UnixMicro()` при `parquet.Timestamp(parquet.Microsecond)`. Для Postgres и MySQL
этого хватает, для ClickHouse `DateTime64(9)` - нет. Достаточно упомянуть в
комментарии, либо выбирать точность по выборке.

### Тестовый стрим дублирует существующий

[`parquet_test.go`](../internal/storage/parquet_test.go#L13)

`sliceStream` почти дословно повторяет `mockRowStream` из
[`storage_test.go`](../internal/storage/storage_test.go#L10) в том же пакете.
Отличается только направлением инициализации `pos`.

### Сравнение ошибки по тексту

[`parquet_test.go`](../internal/storage/parquet_test.go#L90)

`err.Error() != "EOF"` вместо `errors.Is(err, io.EOF)`. Там же игнорируется
возвращённое `n`: если `ReadRows` прочитает меньше строк, `parsed[1]` останется
nil-срезом и следующая строка теста упадёт по индексу вместо внятного сообщения.

### Проглоченная ошибка в тесте

[`manager_test.go`](../internal/core/manager/manager_test.go#L1044)

`store, _ := storage.GetStore(rec.Result.Backend)` - в соседнем
`TestRun_ComputesChecksum` ошибка проверяется. Здесь же `rec.Result`
разыменовывается без nil-проверки, хотя предыдущий тест её делает.

### Checksum не отдаётся на самом скачивании

[`dto.go`](../internal/transport/rest/dto.go#L131)

Значение доступно только через `GET /v1/queries/{id}`, то есть чтобы проверить
скачанный файл, клиенту нужен второй запрос. Просится `Digest: sha-256=...`
или `ETag` на `GET /v1/queries/{id}/result` - хотя бы для ответов без `Range`.

### AGENTS.md разошёлся с кодом

[`AGENTS.md`](../AGENTS.md#L74), [`AGENTS.md`](../AGENTS.md#L91)

«storage backends (`fs`, `s3`) are registered at startup via blank imports» -
бэкендов теперь три, и регистрируются они не blank-импортами, а явными
конструкторами в `main.go`. Там же `instance.default_storage: "fs" or "s3"` -
`clickhouse` теперь тоже валиден.

### Заявленная выгода от условного FS-стора не достигается на своих же конфигах

[`main.go`](../cmd/dbbridge/main.go#L84)

Условие `cfg.Storage.FS.Root != "" || cfg.Instance.DefaultStorage == "fs"`, а
`storage.fs.root` задан во всех поставляемых конфигах, включая
[`deploy/k8s/configmap.yaml`](../deploy/k8s/configmap.yaml) с
`default_storage: s3` и `root: "/data/results"`. Так что `MkdirAll` под
read-only rootfs по-прежнему выполняется. Чтобы выгода появилась, надо ещё и
убрать `storage.fs` из тех конфигов, где результаты уходят в S3.

Отдельно стоит держать в голове совместимость: как только `storage.fs` из конфига
уберут, `fs` перестанет регистрироваться, и старые результаты с

### Имя таблицы ClickHouse подставляется в SQL конкатенацией

[`clickhouse/storage.go`](../internal/storage/backends/clickhouse/storage.go#L34)

`fmt.Sprintf` с `%s` для имени таблицы в DDL, INSERT, SELECT и ALTER DELETE.
Код доPRшный, но именно этот PR впервые делает его достижимым из
`storage.clickhouse.table`. Значение приходит из конфига, то есть от оператора,
поэтому это гигиена, а не уязвимость - но валидацию имени по
`^[A-Za-z_][A-Za-z0-9_]*$` в конструкторе стоит добавить, раз бэкенд
включается.

## Что проверено и выглядит корректно

- **Checksum совпадает с байтами в хранилище** для `fs` и `s3`: оба бэкенда
  байт-прозрачны (`fs` отдаёт `*os.File`, `s3` - тело объекта), `Stat` в обоих
  принимает `ref` по значению и трогает только `SizeBytes`, так что поле переживает
  download-путь. `CountingWriter` обёрнут вокруг `io.MultiWriter`, поэтому
  `ref.SizeBytes` и хэш считаются ровно по одним и тем же байтам, за один проход,
  без чтения результата обратно (I4). Тест `TestRun_ComputesChecksum` действительно
  пересчитывает sha256 по сохранённому файлу, а не по строке из записи.
- **JSONL и CSV переживают round trip через ClickHouse-стор байт-в-байт** - проверено
  запуском на реальном выводе `EncodeStream`, так что checksum для этих пар верен.
- **Per-query `storage_backend` валидируется по живому реестру** в
  [`manager.go`](../internal/core/manager/manager.go#L339), до `pool.Exec` - то есть
  заявленная цель «не падать после выполненного SQL» для override действительно
  выполняется, и снятие безусловной регистрации `fs` её не ломает: запрос получит 400
  на submit, а не ошибку после выполнения.
- **Пустой результат и результат без колонок** дают валидный parquet (0 строк,
  67 и 101 байт соответственно) - проверено запуском, паники или ошибки нет.
- **Обычные дубли имён** (`SELECT 1 AS a, 2 AS a`) работают правильно:
  схема `a`, `a_1`, значения `1`, `2`.
- **NULL, `[]byte`, переход через границу выборки** - проверено запуском,
  ведут себя как заявлено.
- **Порядок defer в `main.go`** корректен: LIFO ставит `qm.Close()` (ждёт in-flight)
  перед `chStore.Close()` и `fsStore.Close()`, так что горутины запросов не пишут
  в уже закрытый стор.
- **Обработка ошибок в `run`** не изменилась к худшему: `encErr` и `closeErr`
  по-прежнему разделены, оба зовут `deletePartial`, checksum ставится только на
  успешном пути.
- **Ранняя валидация `default_storage`** в `config.go` реально ловит
  `s3` без bucket и `clickhouse` без DSN, и неизвестное значение вместо тихого падения
  на первом запросе.
- **Перенацеливание тестов на `avro`** сделано правильно: три места
  (`manager_test.go`, `handler_test.go`, `server_test.go`) продолжают проверять
  отказ на невалидном формате, а не потеряли смысл.
- `go build ./...`, `go vet ./...`, `go test -race -short ./internal/...` и
  `golangci-lint run ./...` - чисто, как и заявлено в описании PR. Файлы
  заканчиваются переводом строки, trailing spaces нет (§14 спеки).
