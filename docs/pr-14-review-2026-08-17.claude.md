# Код-ревью PR #14: feat(authn): require credentials and bind queries to their subject

Дата: 2026-08-17. Ветка `feat/transport-auth` → `fix/transport-contract`, коммит `3bedb44`.

Ревью охватывает только `origin/fix/transport-contract..origin/feat/transport-auth`
(12 файлов, +889/-22). PR четвёртый в стеке из восьми; там, где находка закрывается
дальше по стеку, это отмечено явно.

## Что делает PR

- Новый пакет [`internal/authn`](../internal/authn/authn.go): статические bearer-токены
  из `auth.tokens`, скоупы `read` / `write` / `admin`, `admin` включает остальные.
  Значение токена читается из переменной окружения через `value_env`.
- [`http.go`](../internal/authn/http.go) добавляет chi-middleware и Connect-интерцептор
  (unary + streaming). Неизвестная процедура требует `admin` (fail-closed).
- `QueryRecord.Subject` заполняется в [`manager.go`](../internal/core/manager/manager.go#L415)
  из контекста и проверяется в [`service.authorized()`](../internal/core/service/service.go#L51)
  на путях status / stats / download / stop / watch. Чужой запрос отдаёт 404, а не 403.
- `server.admin_addr` выносит `/metrics` и `/v1/admin/*` на отдельный листенер.
- OpenAPI получает `securitySchemes.bearerAuth` и глобальный `security` с изъятием проб.

## Итог

Ядро сделано аккуратно: интерцептор закрывает и стримы, `ScopeForProcedure` fail-closed,
привязка к субъекту работает через все три транспорта, I1 не нарушен. Но три дыры
пробивают именно то свойство, ради которого PR написан, и одна из них подтверждена
экспериментально: чужой `QueryRecord` (SQL, статистика, локатор результата) отдаётся
по коллизии `Idempotency-Key`. Плюс `/metrics` остаётся без аутентификации при том, что
и код-комментарий, и описание PR утверждают обратное.

Блокеров - 3, важного - 7, мелочей - 11, опровергнуто/переклассифицировано - 4.

## Блокеры

### Коллизия `Idempotency-Key` отдаёт чужому вызывающему полный `QueryRecord`

[`manager.go`](../internal/core/manager/manager.go#L354), [`service.go`](../internal/core/service/service.go#L32)

`StartQuery` - единственный путь, возвращающий `QueryRecord` без вызова `authorized()`.
`resolveIdempotency` ищет ключ по паре `(db_id, idempotency_key)`, субъект в ключ не входит,
а найденная запись возвращается как есть.

Сценарий (проверен запуском на worktree, `internal/transport/rest`):

```
POST /v1/queries  Authorization: Bearer alice-token  Idempotency-Key: shared-key
  {"database_id":"testdb","sql":"SELECT secret_from_alice"}          → 200

POST /v1/queries  Authorization: Bearer bob-token    Idempotency-Key: shared-key
  {"database_id":"testdb","sql":"SELECT bobs_own_sql"}               → 200
```

Второй ответ дословно содержит `"sql":"SELECT secret_from_alice"`, `stats`,
`owner_instance_id` и `result.locator` (полный путь к файлу результата). SQL самого bob
не выполняется вообще - bob получает `query_id`, указывающий на запрос alice, и считает,
что его запрос отработал. Последующий `GET /v1/queries/{id}/result` от bob уже даёт 404,
но утечка текста SQL и локатора уже произошла.

Помимо утечки это ещё и confused deputy плюс DoS: любой subject может занять чужой
`Idempotency-Key` на весь TTL.

Исправление: включить субъект в ключ идемпотентности
(`AcquireIdempotency(ctx, dbID, subject+"\x00"+key, ...)`) - тогда одинаковые ключи
разных субъектов не пересекаются, и I3 сохраняется в границах субъекта. Как минимум -
проверять `authn.AuthorizeSubject(ctx, existing.Subject)` перед `return existing, nil`
и отдавать `NotFoundError`.

Находка доживает до вершины стека (`origin/chore/colima-container-tests`, тот же код).

### `/metrics` смонтирован без `s.require()`, хотя комментарий и описание PR обещают `admin`

[`server.go`](../internal/transport/rest/server.go#L156)

Комментарий на [строках 144-146](../internal/transport/rest/server.go#L144) гласит:
«they are gated on the admin scope wherever they live». Описание PR повторяет:
«With `admin_addr` unset the routes stay on the main router but still require the
`admin` scope». В `mountAdmin` строка 156 - голый `r.Handle("/metrics", telemetry.Handler())`
без обёртки. Тест PR это фиксирует как ожидаемое:
[`server_test.go:370`](../internal/transport/rest/server_test.go#L370) - `{"metrics without a token", ..., http.StatusOK}`.

При дефолтном конфиге (`admin_addr` не задан, ни один поставляемый конфиг его не задаёт)
`GET /metrics` без токена отдаёт 200 на публичном листенере вместе с
`dbbridge_queries_total{engine,db_id,state}`, то есть перечислением всех настроенных
баз и объёма трафика по ним. На отдельном листенере (`SeparateAdmin: true`) - то же самое:
проверено, `GET /metrics` без токена → 200, тогда как `/v1/admin/can-stop` там же → 401.

Сама экспозиция `/metrics` не регрессия - она была и до PR. Регрессия в том, что PR
о безопасности заявляет закрытие этой дыры и не закрывает её, а тест закрепляет 200
как контракт.

Исправление: `r.With(s.require(authn.ScopeAdmin)).Handle("/metrics", telemetry.Handler())`
плюс правка теста; либо честно снять утверждение из комментария и описания и оставить
`/metrics` открытым только при `SeparateAdmin`. Первое предпочтительнее: `admin_addr`
опционален, дефолт не должен быть открытым.

Находка доживает до вершины стека без изменений.

### Секция `auth` невидима для reload: отзыв токена молча не работает, а reload рапортует успех

[`config.go`](../internal/config/config.go#L122), [`diff.go`](../internal/config/diff.go#L11), [`main.go`](../cmd/dbbridge/main.go#L120)

`Authenticator` строится один раз в `main` из снапшота конфига. `NonReloadableChanges`
сравнивает `Instance`, `Server`, `Storage` и `Defaults.MaxConcurrentQueries`, но не `Auth`.

Сценарий: токен утёк, оператор убирает его из `auth.tokens`, делает
`POST /v1/admin/reload` и получает
`{"success":true,"message":"Config reloaded successfully","report":{"ignored":[]}}`.
Токен продолжает работать до рестарта процесса, и ничто в ответе на это не указывает.
`server.admin_addr` таким же образом не применяется, но он хотя бы попадает в `ignored`
как часть `"server"` - `auth` не попадает никуда.

Исправление минимум: добавить в `NonReloadableChanges` сравнение `Auth` и отдавать
`"auth"` в `ignored`. Лучше - пересобирать `Authenticator` на reload через
`atomic.Pointer[Authenticator]`, раз уж это единственный механизм отзыва доступа
в системе без рестарта.

Находка доживает до вершины стека: в `diff.go` на `origin/chore/colima-container-tests`
слова `auth` по-прежнему нет, и `docs/spec.md` §«Reload scope» там перечисляет только
`instance.*`, `server.*`, `storage.*`, `defaults.max_concurrent_queries`.

## Важное

### Авторизация в REST - opt-in на маршрут, и промах отключает не только 401, но и привязку к субъекту

[`server.go`](../internal/transport/rest/server.go#L128), [`authn.go`](../internal/authn/authn.go#L172)

Каждый маршрут гейтится индивидуально через `r.With(s.require(...))`. Новый маршрут,
добавленный без `.With(...)`, молча становится публичным - контраст с
[`ScopeForProcedure`](../internal/authn/http.go#L48), которая для неизвестной процедуры
возвращает `ScopeAdmin`.

Хуже, что промах не деградирует до «просто без 401». `AuthorizeSubject` при отсутствии
identity в контексте возвращает `nil` (fail-open, «аутентификация выключена»), поэтому
маршрут без `require()` читает записи **любого** субъекта. То есть добавление
`r.Get("/queries/{id}/export", ...)` без обёртки даёт анонимный доступ ко всем чужим
запросам, а не только к своим.

Исправление: повесить `s.require(...)` через `r.Use(...)` на группы и снимать только
с проб, либо ввести дефолт-deny на уровне роутера (обёртка над `chi.Router`, требующая
явного скоупа при регистрации). Отдельно стоит различать «аутентификация выключена
глобально» (флаг у сервиса) и «identity не попала в контекст» - второе должно быть deny.

### 401/403 идут мимо единого конверта ошибок API

[`http.go`](../internal/authn/http.go#L20), [`errors.go`](../internal/transport/rest/errors.go)

Весь REST отдаёт `errorResponse{error, request_id}` с `Content-Type: application/json`.
`Middleware` использует `http.Error`. Проверено:

```
GET /v1/databases (без токена)
  → 401  Content-Type: text/plain; charset=utf-8  body: "unauthorized\n"
```

`request_id` теряется, клиент не может распарсить ошибку тем же кодом, что и остальные.
В OpenAPI ни у одного пути нет `responses: "401"` / `"403"` - только прозаическое
упоминание в `description` схемы `bearerAuth`
([`dbbridge.yaml`](../api/openapi/dbbridge.yaml#L390)), то есть генерируемые клиенты
об этих кодах не узнают.

Исправление: вынести запись ошибки в колбэк (`Options.WriteError`) либо перенести
middleware в `internal/transport/rest`, где `writeStatus` уже есть; в OpenAPI добавить
общий компонент `responses.Unauthorized` / `Forbidden` и сослаться на него.

### `/v1/ws` теперь недостижим ровно для браузерных клиентов, ради которых он существует

[`server.go`](../internal/transport/rest/server.go#L130)

Маршрут гейтится `s.require(authn.ScopeRead)`, то есть требует заголовка
`Authorization`. Браузерный `WebSocket` API не позволяет задать заголовки при handshake.
Проверено: `GET /v1/ws` без заголовка → 401 ещё до `websocket.Accept`.

При этом `Options.WSAllowedOrigins` и проверка Origin в
[`ws/server.go`](../internal/transport/ws/server.go#L66) существуют исключительно
для браузерных клиентов - без них проверка Origin бессмысленна. Получается
взаимоисключающая пара.

Исправление: принять токен через `Sec-WebSocket-Protocol` (`coder/websocket` это
поддерживает через `AcceptOptions.Subprotocols`) или выдать одноразовый ticket
отдельным аутентифицированным эндпоинтом. Токен в query string брать не стоит - он
попадёт в логи доступа.

### `internal/core/manager` теперь линкует `connectrpc.com/connect`

[`authn.go`](../internal/authn/authn.go#L1), [`http.go`](../internal/authn/http.go#L8)

Doc-комментарий пакета заявляет: «It lives outside internal/transport because ...
core must not import a transport». Но `http.go` в том же пакете тянет
`net/http` и `connectrpc.com/connect`, а `manager.go` импортирует `authn`. Проверено:

```
$ go list -deps ./internal/core/manager | grep -c connectrpc.com/connect
2
```

То есть ядро исполнения запросов транзитивно зависит от Connect-рантайма. Это ломает
и заявление в комментарии, и §2 спеки («Layers are strictly separated by interfaces,
so that in v2 QueryManager can be moved to a separate durable daemon»).

Исправление: оставить в `internal/authn` только `Identity`, `Scope`, `Authenticator`,
контекст и `AuthorizeSubject`; middleware вынести в `internal/transport/rest`,
интерцептор - в `internal/transport/grpcconnect`. `ScopeForProcedure` тоже транспортная
деталь и место ей рядом с интерцептором. Диффа это добавит мало, зависимость снимает
полностью.

### Admin-роутер не наследует middleware публичного роутера

[`server.go`](../internal/transport/rest/server.go#L148)

`s.adminRouter = chi.NewRouter()` без `middleware.RequestID`, `Logger`, `Recoverer`,
`ClientIPFromXFF`. Последствия на admin-листенере:

- `writeStatus` пишет `middleware.GetReqID(r.Context())` == `""`, поле `request_id`
  исчезает из конверта ошибки (`omitempty`), а `writeError` логирует `request_id=`
  пустым - корреляция админских ошибок теряется;
- запросы к `/v1/admin/*` и `/metrics` не логируются вообще;
- паника в `handleReloadConfig` перехватывается только recover'ом из `net/http`
  (процесс выживает), но клиент вместо 500 получает оборванное соединение и стек
  уезжает в лог в чужом формате.

Исправление: вынести общий набор `Use(...)` в хелпер и применить к обоим роутерам.

### Включение auth на живом деплое делает все ранее созданные запросы недоступными их владельцам

[`models.go`](../internal/core/domain/models.go#L167), [`authn.go`](../internal/authn/authn.go#L172)

Записи без `Subject` доступны только `admin` - это осознанное решение и оно описано
в PR. Но операционное следствие не покрыто: в момент включения `auth` (или в середине
rolling-деплоя, когда часть инстансов ещё пишет записи без субъекта) все существующие
записи, включая выполняющиеся прямо сейчас, начинают отдавать 404 своим владельцам.
Скачать результат уже запущенного длинного запроса станет невозможно.

Исправление: описать порядок включения в документации (сначала выкатить бинарь,
дождаться истечения `result_ttl`, потом включить `auth`), либо ввести переходный режим
`auth.legacy_records: open|admin_only` со сроком жизни в один релиз.

### Дыры в тестах

[`server_test.go`](../internal/transport/rest/server_test.go#L451)

- `TestREST_SeparateAdminListener` строит сервер как `rest.Options{SeparateAdmin: true}`

- Нет теста на `/v1/ws` с токеном и без (маршрут получил новый гейт, поведение не

- На Connect-поверхности проверяются только скоупы; привязка к субъекту (чужой

- Нет теста на коллизию `Idempotency-Key` между субъектами (см. первый блокер).
- `{"metrics without a token", ..., 200}` закрепляет дыру как контракт.
- В `internal/config` нет теста на валидацию `auth` (пустой список токенов).

## Мелочи и предложения

### `Authenticate` не constant time в том смысле, который обещает комментарий

[`authn.go`](../internal/authn/authn.go#L129)

`subtle.ConstantTimeCompare` возвращает 0 сразу при несовпадении длин. Итоговое время
цикла зависит от того, сколько настроенных токенов имеют ту же длину, что и предъявленный,
то есть утекает длина каждого токена. Комментарий на строках 126-128 утверждает, что
«neither the time nor the control flow reveals which token was close to matching».
Практическая эксплуатируемость по сети близка к нулю, но заявление стоит либо
привести в соответствие, либо сравнивать SHA-256 от значений - тогда длины
выравниваются бесплатно.

### `Authenticate` отдаёт слайс скоупов по ссылке на внутреннее состояние

[`authn.go`](../internal/authn/authn.go#L142)

`Scopes: a.tokens[match].scopes` - общий бэкинг-массив. `append` реаллоцирует
(cap == len после `make([]Scope, 0, len(...))`), так что случайно испортить не выйдет,
но `id.Scopes[0] = ScopeAdmin` перепишет права токена на весь процесс. Ни один вызывающий
сейчас так не делает. Дёшево закрыть через `slices.Clone` или заменить слайс на битовую
маску.

### `New` не проверяет силу значения токена

[`authn.go`](../internal/authn/authn.go#L80)

Валидируются subject, скоупы, дубликаты и непустота env, но `value: "x"` принимается.
Троттлинга неудачных попыток в этом PR нет (появляется ниже по стеку в PR #19
`feat/rate-limit`), поэтому в границах этого коммита односимвольный токен подбирается
брутфорсом. Минимальная длина (32 байта) в `New` - одна строка.

### `value` и `value_env` одновременно: молчаливый приоритет

[`authn.go`](../internal/authn/authn.go#L89)

`ValueEnv` перекрывает `Value` без предупреждения. Оператор, оставивший inline-значение
и добавивший `value_env`, не узнает, какой из двух реально действует. Стоит вернуть ошибку.

### Нет `Vary: Authorization` на ответах

[`http.go`](../internal/authn/http.go#L27)

Ответы теперь зависят от субъекта, а заголовок, запрещающий промежуточному кешу
переиспользовать их между вызывающими, не выставляется. Для сервиса за LB это
одна строка в middleware.

### `write` не включает `read`

[`authn.go`](../internal/authn/authn.go#L62)

Токен только с `write` может отправить запрос, но не может посмотреть его статус или
скачать результат: `GET /v1/queries/{id}` требует `read`. Работает только `mode: sync`.
Это защитимо, но неочевидно и нигде не сказано; либо задокументировать, либо сделать
`write` надмножеством `read` по аналогии с `admin`.

### `admin` смешивает «управлять процессом» и «читать чужой SQL»

[`authn.go`](../internal/authn/authn.go#L27)

Токен оркестратора, которому нужен только `/v1/admin/can-stop`, автоматически получает
чтение SQL и результатов всех субъектов. Разделение на `admin` (reload, can-stop) и
отдельный `read:all` убрало бы это.

### `StopQuery` и `WatchQuery` читают запись из MetaStore дважды

[`service.go`](../internal/core/service/service.go#L66), [`manager.go`](../internal/core/manager/manager.go#L771)

`authorized()` делает `GetQuery`, затем `qm.StopQuery` (строка 771) и `qm.Watch`
(строка 820) делают его ещё раз. Три остальных пути (`GetQueryStatus`, `GetQueryStats`,
`DownloadResult`) переиспользуют уже полученную запись. На redis-метасторе это лишний
round-trip на каждый вызов. Логика от этого не ломается (`Subject` не меняется), но
асимметрия выглядит как недоделка.

### 405 отдаётся до проверки токена

[`server.go`](../internal/transport/rest/server.go#L159)

`GET /v1/admin/reload` без токена возвращает 405 с пустым телом (chi обрабатывает
method-not-allowed до route-middleware), тогда как `GET /v1/databases` без токена -
401. Неаутентифицированный вызывающий может перечислять существующие маршруты и их
методы. Мелочь, но при желании закрывается общим `r.Use` вместо `r.With`.

### Долгоживущие соединения не перепроверяют токен

[`http.go`](../internal/authn/http.go#L97), [`ws/server.go`](../internal/transport/ws/server.go#L84)

Identity фиксируется на handshake. WS-соединение и Connect-стрим (`WatchQuery`,
`DownloadResult`) переживают отзыв токена сколь угодно долго. Стандартный компромисс,
но стоит упомянуть в документации вместе с тем, что отзыв и так требует рестарта
(см. третий блокер).

### Makefile-таргеты admin API перестанут работать при включённом auth

[`Makefile`](../Makefile#L108)

`make reload-config` и `make can-stop` дёргают `/v1/admin/*` через curl без заголовка
`Authorization`. Пока в поставляемых конфигах нет секции `auth`, они работают; после
включения вернут 401 без подсказки. Достаточно `-H "Authorization: Bearer $$DBBRIDGE_ADMIN_TOKEN"`.

## Что проверено и выглядит корректно

- **Connect-интерцептор покрывает обе поверхности.** `WrapUnary` и `WrapStreamingHandler`
  ([`http.go`](../internal/authn/http.go#L78)) - серверные стримы `DownloadResult` и
  `WatchQuery` идут через второй хук и действительно закрыты, тест это подтверждает.
  `WrapStreamingClient` - pass-through, `req.Spec().IsClient` корректно исключает
  клиентскую сторону.
- **`ScopeForProcedure` fail-closed и полный.** Все 9 RPC из
  `api/proto/dbbridge/v1/dbbridge.proto` присутствуют в `procedureScopes`; неизвестная
  процедура → `ScopeAdmin`, тест на `SomethingNew` есть.
- **Привязка к субъекту работает через все три транспорта.** Все хендлеры
  `grpcconnect` ходят через `svc.*`, а не мимо; WS протаскивает identity через
  `r.Context()` → `subCtx` → `svc.WatchQuery`, то есть `authorized()` вызывается и там.
- **404 вместо 403 на чужой запрос** - существование ID не подтверждается,
  проверено тестом и вручную.
- **I1 не нарушен.** Identity не попадает в `execCtx`: он строится от
  `context.Background()` ([`manager.go`](../internal/core/manager/manager.go#L388)),
  так что отзыв токена или обрыв клиента не отменяет выполняющийся запрос.
- **Fail-closed на старте.** `config.validate` отбивает `auth:` с пустым списком токенов,
  `authn.New` - все нерабочие спеки, `main` падает через `log.Fatalf`. Это правильный
  выбор направления отказа.
- **`AdminHandler()` возвращает настоящий nil-интерфейс**, а не typed-nil
  ([`server.go`](../internal/transport/rest/server.go#L89)), проверка
  `if h := restServer.AdminHandler(); h != nil` в `main` работает как задумано.
- **Admin-листенер вписан в graceful shutdown** ([`main.go`](../cmd/dbbridge/main.go#L263)),
  таймауты те же, что у остальных серверов.
- **Пробы остались открытыми** и помечены `security: []` в OpenAPI - kubelet и LB
  не сломаются.
- **Роутинг не сломался** от выноса `/v1/admin` из подроутера `/v1` в отдельный
  `Route("/v1/admin", ...)` на верхнем уровне: chi выбирает более длинный статический
  префикс, `go build ./...` и `go test ./internal/authn/... ./internal/transport/...
  ./internal/config/...` проходят.

## Опровергнутые находки

### «Bearer-токены передаются открытым текстом, TLS нет нигде»

Утверждение верно для этого коммита, но это не находка против PR #14. Отсутствие TLS -
пре-существующее состояние (`SetUnencryptedHTTP2(true)` в `main.go` появился раньше),
а `server.tls` с `cert_file` / `key_file` / `allow_h2c` добавляется ниже по стеку в
PR #17 (`chore/deploy-hardening`), который правит `cmd/dbbridge/main.go`,
`internal/config/config.go`, `deploy/Dockerfile` и добавляет `deploy/k8s/secret.yaml`.
Требовать TLS в рамках PR #14 значит требовать переделки границ стека. `servers:
- url: http://localhost:8080` в OpenAPI помечен `description: Local development` и тоже
не менялся этим PR.

### «Ни один поставляемый конфиг, ConfigMap или blue/green не упоминает auth и admin_addr»

Факт подтверждается (`grep` по `configs/`, `deploy/`, `docs/` в этой ветке ничего не
находит), но закрывается ниже по стеку тем же PR #17: `configs/dbbridge.yaml` там
получает закомментированные `admin_addr: ":8081"` и блок `auth.tokens` с `value_env`,
плюс `deploy/k8s/secret.yaml`. `prometheus.io/port: "8080"` в `deploy/k8s/deployment.yaml`
корректен ровно потому, что `admin_addr` в поставляемых конфигах не задан. Как блокер
PR #14 не засчитывается.

### «AGENTS.md и docs/spec.md не описывают новую подсистему»

Подтверждается для этой ветки, но закрывается в PR #20 (`docs/spec-code-alignment`):
на вершине стека `AGENTS.md` содержит строку про `internal/authn` и скоупы, а
`docs/spec.md` - раздел про bearer-токены, скоупы и `internal/authn/` в структуре
репозитория. Единственное, что в документацию так и не попало, - что `auth` не
перезагружается (см. третий блокер).

### «Мутация `Identity.Scopes` перепишет права токена на весь процесс»

Механизм описан верно, но эксплуатируемость завышена: `scopes` создаётся как
`make([]Scope, 0, len(spec.Scopes))` и заполняется ровно `len` раз, поэтому `append`
у вызывающего реаллоцирует и внутреннее состояние не трогает. Испортить можно только
прямым присваиванием по индексу, чего ни один вызывающий не делает. Оставлено как
мелочь-хардening, не как баг.
